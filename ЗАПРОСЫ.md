# Какие запросы нужны для расчёта доли ИИ

Данные берутся из двух мест. Диалоги — по обычному API, заказы — только
через инструмент CRM (прямого API для заказов нет, проверено: отдаёт HTML).

## 1. Диалоги с сообщениями — HTTP API

```
POST https://crm.easy-mo.ru/external/v1/customers/dialogs/export
Authorization: Bearer <токен>
Content-Type: application/json

{
  "date_from": "2026-11-09",
  "date_to":   "2026-11-09",
  "department_ids": [122],
  "page": 1,
  "per_page": 100
}
```

Ограничения, проверены на практике:

- фильтр работает по **дате создания клиента**, а не по дате сообщений;
- **только один день** за запрос: `date_from` и `date_to` должны совпадать;
- **только один отдел** за запрос, иначе HTTP 422 `dialogs_limit_exceeded`;
- `per_page` не больше 100, число страниц берётся из `pagination.last_page`;
- `pagination.total` за день равен числу лидов на панели CRM — сверено:
  книги 1066, Зарина 755, портреты 623.

В ответе у каждого сообщения есть `sender_type`, `sender_name`, `sent_at`,
`text`, `message_id`. У заказа внутри диалога только `order_id`,
`created_at`, `manager`, `amount`, `prepayment`, `products` — **даты перевода
на ведение там нет**, поэтому нужен второй запрос.

Отделы: 122 Фотокниги Алина и Регина, 126 Статуэтки Зарина,
128 Статуэтки Диана и София, 127 Статуэтки Ангелина,
10 Портреты Настя и Руслан.

## 2. Заказы с датой перевода на ведение — инструмент CRM

```
get_orders
  department_names: ["Фотокниги Алина и Регина"]
  date_field_name:  "Дата перевода на ведение"
  date_from:        "2026-11-10"
  date_to:          "2026-11-10"
  per_page:         200
```

`date_field_name` подставляет любое поле заказа типа «дата», и тогда
`date_from`/`date_to` применяются к нему вместо даты создания заказа.
Поле называется «Дата перевода на ведение», field_id 40, хранит только
дату без времени. Рядом есть «Переведен на ведение вручную» (field_id 41).

В ответе берём `customer.id` и значение поля 40 — этого хватает.

**Что нужно от разработчика:** тот же фильтр в обычном API. Сейчас
`/external/v1/orders` и `/external/v1/orders/export` на POST отвечают 405,
на GET отдают HTML веб-интерфейса. Без этого ежедневный агент не может
считать сам — границу оформления ему взять неоткуда.

## 3. Как считается

1. Заказы с «Датой перевода на ведение» = нужный день.
2. Оставляем тех, чей лид пришёл не раньше чем за 7 дней до этого дня.
3. У каждого клиента берём сообщения до конца дня перевода.
4. Раскладываем каждое сообщение:
   - `sender_type` = `arthur_ai` или `bot` → **ИИ**
     (на экране CRM это «Артур Бот» и «Геннадий Горин (Бот)»);
   - `sender_type` = `client` → не считается;
   - имя содержит «роп» (роповские учётки) → **выкидываем совсем**,
     ни в числитель, ни в знаменатель: это рассылки руководителей;
   - всё остальное → **менеджер**, даже если человек копирует скрипт бота.
5. Доля ИИ = ИИ / (ИИ + менеджеры).

Второй срез считается так же, но выборка — все лиды, пришедшие в заданный
день; у тех, кто до ведения не дошёл, оформление ещё идёт, берём всё.
